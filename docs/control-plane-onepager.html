A control plane that lets an LLM service answer the grid

A Kubernetes operator watches for a demand-response event, then turns the knobs the serving software already exposes — stop admitting low-priority requests, drain a GPU pool to idle, scale replicas — until the measured GPU power meets the budget, while latency alarms protect the users who matter. Because prompt-reading (prefill) and answer-writing (decode) run on separate pools, the operator also chooses which pool to cut: that choice is the control surface disaggregated serving creates, and the reason this project exists alongside its measurement twin. It is a thermostat: you declare the temperature you want (a power budget), it reads the thermometer (GPU telemetry), and it keeps nudging the furnace (the serving cluster) until the two agree.

Cloud: GKE, one zonal cluster, Terraform GPU: 1× T4 Spot live · two pools in simulation Serving: vLLM · Qwen2.5-1.5B Operator: Python / kopf · custom resource Status: week 3 · plan v2, nothing provisioned

The question

Grids increasingly pay large users to shed load on request. Emerald AI's field trials have shown AI datacenters can do it for training jobs by setting GPU power caps. Interactive inference is harder: a cap needs root on every node, and users are waiting on the other end. This project asks whether a software-only control plane — one an operator could actually run on a cloud cluster — can hit a declared power budget on a live LLM service, fast, without breaking its latency promise to premium users.

One event, start to finish

t = 0

Event arrives

A replayed ERCOT price spike lands on a Pub/Sub topic: "shed to 60% of nominal for 30 minutes." The operator turns it into a PowerBudget object in the cluster.

t + 2 s

Operator reconciles

Reads the target, the current watts from Prometheus, and the lever curves. Picks the cheapest lever that closes the gap: stop admitting flex-tier requests.

t + 10 s

A pool drains

The operator cuts the prefill pool first: deepest watts per GPU (~230 → 40 W) and it costs only time-to-first-token — answers already in flight keep streaming from the decode pool. If the gap is still open, scale a decode replica down.

t + 30 s

Telemetry confirms

DCGM shows watts under budget; vLLM metrics show premium p99 still inside its objective. The burn-rate alert stays quiet. The operator holds.

t + 30 min

Recovery

Budget expires. Flex admission reopens gradually — a ramp limit so the backlog does not spike power above baseline. Every decision is logged for the report.

Why this project

For the course

  • A custom Kubernetes resource and operator with a real reconcile loop — the pattern Kubernetes' own controllers use.
  • Infrastructure as code, managed observability with SLOs and burn-rate alerting, managed messaging, GPU scheduling, Spot economics and teardown discipline.
  • Evaluated twice with the same code: on the live T4 to prove the wiring, on a simulated two-pool cluster to make the quantitative claims — including the one that matters, whether cutting prefill or decode first holds the SLO at a given budget.

Beyond the course

  • This is the shape of Emerald AI's Conductor product, built for the inference case their field paper calls out as open — and on Kubernetes rather than their SLURM stack.
  • The DSCI-650 project measures what the levers do; this project builds the hand that pulls them. Together they are one programme: measurement and control.

Known constraints, settled up front: GPUs are unavailable on a GCP free trial (paid billing and a quota request first); the T4 is a 70 W card, so it demonstrates the mechanism rather than the magnitude; the gateway extension's priority API is alpha, so admission starts as a small proxy; mean power below the limit is not headroom — the operator reads the driver's throttle flag from DCGM instead.
