Jade: measuring what an LLM serving system can give back to the grid

Project proposal · DSCI-650 High Performance Data Science, Fall 2026 · Karthik Mattu (km5503@rit.edu) · solo

Problem and question

Grid operators pay large electricity users to shed load on request, and AI datacenters would like to say yes. Emerald AI's 2026 field trials show it works for training by capping GPU power. Interactive inference is the open case: their paper, and the BU PEAC Lab's e-Energy '26 study, both list inference latency boundaries, prefill/decode decomposition and rebound as future work. Nobody has measured, on a real serving stack, which part of an LLM service you can turn down, how much power that returns, how fast, and what it costs the people waiting for an answer.

For interactive LLM serving, how much power can be shed, how fast, and at what cost to p50/p99 latency — using only the knobs the serving software exposes — and how does splitting prefill from decode across GPUs change the answer?

An LLM answers a request in two phases with opposite profiles. Prefill reads the whole prompt at once: compute-bound, brief, the GPU's highest draw. Decode writes the answer one token at a time: memory-bandwidth-bound, long, lower draw. Modern serving systems (vLLM, llm-d, NVIDIA Dynamo) can run the two on separate GPU pools. If the phases have different power signatures, that split hands an operator a control surface a single server does not have. Jade measures whether that is true, by how much, and what using it costs.

System

  1. 1A multithreaded C++ load generator replays an identical tiered trace (premium / flex) at a controlled request rate, so every configuration sees the same work.
  2. 2In E2/E3 an MPI harness runs the experiment: rank 0 replays a grid event and issues lever commands asynchronously; one rank per GPU samples power and actuates vLLM; cluster power is a collective.
  3. 3vLLM serves the model; from E2 on, prefill and decode run on separate A100s with the KV cache handed between them. Each GPU rank reads watts, clock and the driver's throttle flag through NVML's C API.
  4. 4The probe attributes energy to phases by direct division on near-pure windows, and gates its own cross-check: if a regression cannot recover the measured baseline, its coefficients are not quoted.
  5. 5Every window feeds the experiments. E1.5's CUDA kernels are metered by the same probe, giving the silicon's joules per byte and per FLOP — the first-principles model the vLLM numbers are checked against.
  6. CThe output is one JSON file of lever curves. My Modern Cloud Computing project consumes it as policy (see below); nothing else crosses.

How this uses the course technologies

The serving engine (vLLM) is a Python service treated as a black box over HTTP. Everything that measures it, drives it and controls it is written in C++ against the three course modules. Components are built in the order the experiments need them; where that runs ahead of the corresponding module, I learn the material early.

What is already measured (weeks 2–3, one A100)

  • Draining is the lever. Busy 197–230 W, parked with the model loaded 39–43 W: stop sending a GPU work and ~80 % of its draw is gone in seconds.
  • The 250 W limit binds on prefill, not decode — by the driver's own throttle flag, set ~90 % of the time in prefill-heavy windows and 0 % in small-batch decode. A prefill window averaging 230 W was still capped 90 % of the time: mean-below-limit is not headroom.
  • Decode costs ~27× more energy per token than prefill yet draws less power; batching cuts decode joules per token 25× from batch 1 to 32 while raising mean power — an efficiency lever, not a power lever.

Project Update I lands after E1 (the C++ probe validated against the prototype); Update II after E2/E3; the paper is drafted from week 12. The distributed content is E2 and E3: two GPUs serving one model as separate pools with inter-process KV-cache transfer, an MPI controller coordinating per-GPU ranks, tier-aware admission, and a policy that has to reason about which pool to cut. If queues allow, E2b runs the same harness across two nodes. Reported metric: QoS cost per watt shed — the same family as my CoordDR work on moving load between datacenters, so the two studies share a vocabulary.

Relationship to my Modern Cloud Computing project

My other class project this term (with Prof. Fang) builds a Kubernetes operator on GKE that enforces a declared power budget on a live vLLM deployment by pulling these same levers automatically. The only thing the two projects share is one JSON file — the lever-curve schema, values as fractions of nominal GPU power. That project runs on synthetic curves from day one and is complete without Jade's results; Jade's measurements are complete without the operator. Shared: problem domain, vLLM, the Qwen2.5 model family, NVIDIA power telemetry as the measured quantity. Not shared: code, compute, experiments, or any graded artifact. I am glad to adjust the split if you would prefer a cleaner separation.
